# MAM wash-cup shared memory 对话 Token 用量审计

## 1. 结论

本报告审计 Codex 对话 `MAM - wash-cup shared memory` 及其派生 subagent 在最近 24 小时内的模型调用。采样时间约为 2026-09-11 18:18（Asia/Shanghai）；目标对话当时仍为 active，因此滑动窗口中的数字会随时间小幅变化。

本窗口共记录约 5,574 次模型请求、6.95 亿 input token 和 302 万 output token。按 OpenAI 官方 API 单价估算约为 625 美元，与账单中约 640 美元的观察基本一致。差额可能来自统计窗口边界、仍在完成的请求及账单聚合时间。

逐请求分类后，约 2,094 次、275 美元属于没有实质动作的纯轮询；另有约 654 次、93 美元同时包含状态处理和继续等待；约 2,826 次、257 美元明确用于实现、验证、分析、派发、审阅或回答。合理估计约 320–340 美元可以通过事件驱动等待、缩短上下文和避免使用高价模型轮询而省去。

因此，本次消耗大致是一半来自任务难度和实际工程工作，一半来自 active-turn 管理方式。主要问题不是 subagent 数量本身，而是少数 Manager/monitor agent 长时间保持 active，并以 30–60 秒间隔反复向模型发送约 10–15 万 token 的上下文。

## 2. 审计范围与数据来源

审计对象：

- 根对话 ID：`01a081fe-d6c2-74f2-a73d-68584e9d915b`

费用不是从账单接口导出的最终结算值，而是根据逐请求 token 记录和请求发生时的模型设置计算的 API 等价费用。官方单价为：

| 模型 | 非缓存 input / 1M | cached input / 1M | output / 1M |
| --- | ---: | ---: | ---: |
| GPT-6 Astra | $10.00 | $1.00 | $50.00 |
| GPT-5.6 Terra | $2.00 | $0.20 | $12.00 |

价格来源：[GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)、[GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)。窗口内没有 input 超过 272K 的请求，因此估算未涉及超长上下文加价；观察到的 service tier 均为 `default`。

单次请求的估算公式为：

```text
费用 = (input - cached_input) × 非缓存 input 单价
     + cached_input × cached input 单价
     + output × output 单价
```

`reasoning_output_tokens` 是 `output_tokens` 的子集，没有重复计费。

## 4. 逐请求分类方法

本报告没有把整个长 turn 粗略算作轮询，而是逐个 `token_usage_record` 检查该次模型响应产生的动作。

### 4.1 纯轮询

一次响应只进行以下动作，且没有实质用户回复或其他工具调用：

- 调用 `wait`、`wait_agent`、`wait_threads`；
- 调用 sleep；
- 对已有长命令执行空的 `write_stdin`；
- 通过包装工具继续等待 subagent 或 `mam wait jobs`。

典型响应只输出约 31 个 token，用来再次调用 `wait`，但 input 仍可能达到 13–18 万 token。

### 4.2 混合监控/工作

同一次响应既包含等待动作，也包含至少一项状态处理或有效输出，例如：

- 读取训练日志、loss、step、ETA 或 GPU 状态后继续等待；
- 接收 subagent 结果、作出简单判断后继续等待；
- 向用户发送进展，再进入下一次 wait；
- 同时包含状态命令和等待调用。

这部分不能全部视为浪费，因为它承担了训练收尾、异常发现和调度职责；其中的高频唤醒和重新携带上下文仍可由确定性 watcher 替代。

### 4.3 明确干活

响应不包含等待调用，或者主要执行以下工作：

- 读取和修改代码、文档或任务要求；
- 执行测试、分析日志和定位故障；
- 创建、绑定和派发 MAM task；
- 启动实现或独立 review；
- 处理实验设计、架构讨论和用户问题；
- 交付报告、提交和验收结论。

合计与总分类相差约一次，是因为根对话仍在运行且统计窗口持续滑动。

账单中观察到每次轮询约 0.07 美元，可以对应较短上下文、两种模型的局部混合或某个具体时段；整个窗口的纯轮询平均值更高，是因为约 91% 的纯轮询实际使用了 Astra。一次包含约 13 万 cached input 的 Astra 请求，仅缓存输入费用就约为：

```text
130K × $1 / 1M ≈ $0.13
```

Terra 的 cached input 单价只有 Astra 的五分之一，所以类似上下文的一次纯轮询约为 0.03–0.04 美元。降低轮询模型等级的收益很大，但最佳方案仍是取消模型级轮询。

## 8. 实际工作与任务价值

窗口内新派发约 24 个 subagent，涉及 18 个可识别的正式 MAM task；采样时 18 个任务均已有 report，其中 10 个为独立 review，13 个已归档、5 个仍待最终处理。

主要工作包括：

- wash-cup/shared-memory 数据、训练和 checkpoint 验收；
- 多种 memory 表示和时序协议的训练、offline/live 路径检查；
- RMBench、OpenPI、robot-bridge 多仓库集成和 review；
- 多机 GPU 训练、评测调度和结果收尾；
- 公共 RPC 超时、schema、部署依赖和集群 C 环境排障；
- MAM 多项目隔离、发布分支、task revision 等实现和审阅；
- 实验台账和论文证据整理。

这些任务涉及多仓库、多台机器、GPU 长进程、训练与评测、真机路径和独立验收，本身确实具有较高难度。约 257 美元明确用于实质工作，与完成的工程量基本匹配。小型独立 review 通常只消耗 1–5 美元，能够减少错误训练、错误合并或真机部署风险，并不是本次费用异常的主要来源。

真正异常的是把 LLM turn 当作长进程守护器：根 Manager、训练 owner 和 eval owner 同时常驻，每隔几十秒由模型决定“继续等待”。该模式同时放大了请求数和每次请求携带的上下文。

## 9. 使用方式中的主要问题

### 9.1 `保持 active turn` 被实现成模型级轮询

用户要求保持 active turn 的原意是避免错过 subagent 完成消息。实际执行中，Manager 和部分 worker 反复调用 wait/sleep，每次工具返回后都再次调用模型。即使模型只输出下一次 wait，仍会重新计入完整 input。

### 9.2 监控 agent 使用了 Astra

Locke、Nietzsche 等 worker 最初按 Terra 派发，部分时段的实际 thread setting 后来切换为 Astra。训练状态检查和等待不需要旗舰模型，却贡献了绝大多数纯轮询费用。

### 9.3 单个对话上下文持续增长

根对话从更早的长对话 fork 而来，又不断吸收完整任务要求、报告、源码、日志、subagent 通知和设计讨论。即使缓存命中，每次请求仍要为十多万 cached token 付费。

### 9.4 多层常驻监控

当前结构接近：

```text
根 Manager 常驻
├── 训练 owner 常驻并轮询
├── eval owner 常驻并轮询
└── 实现/review worker 执行实际任务
```

多个层级都在为同一批长进程支付轮询和上下文费用。

## 10. 改进建议

### 10.1 将等待移到进程和事件层

- Worker 启动超过一小时的任务并完成 `mam job add` 后结束当前模型 turn。
- 使用一个长时间的 `mam wait jobs`、阻塞式 thread wait 或确定性 watcher 等待状态变化。
- 只有 job 完成、失败、长时间无进度或需要决策时才唤醒模型。
- subagent 完成通知集中发送给根 Manager，不要求每个 owner 为接收通知持续 active。

### 10.2 合并训练和评测监控

- 一个脚本批量读取全部 job 的 PID、step、loss、ETA、日志更新时间和 GPU 状态。
- 正常运行时不调用模型；异常或完成时生成一份统一摘要。
- 不再每小时分别唤醒十余个 owner，也不重复读取已经通过的 smoke 或恢复验证。

### 10.3 固定模型职责

| 工作类型 | 建议模型/工具 |
| --- | --- |
| 架构设计、复杂根因分析、最终裁定 | Astra |
| 代码实现、重要独立 review | Terra |
| 日志整理、简单状态解释 | Luna/Terra low |
| PID、GPU、step、loss、文件完整性巡检 | Shell watcher，不调用模型 |

监控 agent 不应在运行中自动或手动升级到 Astra，除非检测到需要复杂分析的异常。

### 10.4 控制上下文生命周期

- 每个阶段通过 MAM `task.md`、`report.md` 和实验台账交接，不依赖完整聊天历史。
- 新 subagent 使用空白或最小上下文，只获得 TASK-ID、仓库位置和必要约束。
- 根对话达到约 50K–80K 有效上下文或进入新的实验阶段时，生成简洁 handoff 后迁移到新对话。
- 命令只返回必要行，避免把完整 README、源码、长日志或重复报告注入 Manager 上下文。

### 10.5 增加预算保护

- 单 turn 超过 100 次模型请求时告警。
- 单 turn 连续等待超过 30 分钟时转为事件等待。
- 单 turn cached input 超过 10M 时要求 compact 或迁移。
- 监控类 agent 每日预算不超过 10 美元。
- 普通 worker 建议单任务预算 10–20 美元。
- 根 Manager 达到 50 美元时提示检查常驻轮询和上下文长度。
- 每次切换到 Astra 时记录用途，监控任务默认拒绝升级。

## 12. 统计限制

- 目标对话在采样时仍为 active，精确数字随滑动窗口变化。
- “混合监控/工作”包含必要判断和可替代轮询，无法仅凭工具类型精确拆分价值。
- 本报告按当前官方 API 标准价格估算，不代表订阅套餐内部额度的结算方式。
- Rollout 记录能够准确给出逐请求 token，但不能自动判断每次工程判断的业务价值；价值结论结合了任务报告、派发目的和工具轨迹。
- 纯轮询采用保守定义，没有把普通日志读取、状态分析或用户进展回复算入纯轮询，因此 275 美元可视为明确轮询成本，而不是所有潜在可优化成本。

### 13.5 使用该口径时的注意事项

- 表中 TASK-ID 费用是执行者直接成本，不是“全成本”；Manager 设计任务、读报告、派发 review、合并和等待的 231 美元仍在控制面。
- 不建议按 task 直接费用比例机械分摊 Manager 成本。Manager 的一个 turn 经常同时处理训练、评测、MAM 修改和用户讨论，比例分摊会制造虚假的精确度。
- 对长训练 task，应进一步拆分“启动与验收”和“运行期监控”。训练运行本身不消耗模型 token，只有 agent 反复检查训练才消耗 token。
- 任务状态是采样时状态；`pending` 不代表没有交付，部分任务已有 report，但尚未由 Manager 归档。
- 没有在本 24 小时窗口产生模型请求的历史 task 不在表中。
